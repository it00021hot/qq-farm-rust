## 5. 几个需要决策的点

1. **是否保留原 `core/src/services/activity-center.ts` 全部 1034 行？** 那是活动中心，活动时效性强，**很多是过期活动代码**。我建议**只复刻架构 + 当前生效的 2~3 个活动**，把过期代码作为注释标注 / 直接不写。
2. **是否复刻 `controllers/admin/farm-routes.ts` 1400 行？** 这 1400 行里有大量**前端 Vue 组件期望的 API**（推测是历史兼容性堆的）。建议**对齐前端实际调用 + 删冗余**，而不是无脑 1:1。
3. **types/ 层是否真要建？** Rust 通常用各模块内部 struct 就够了。原 TS 之所以有 types/ 是因为 TS 类型系统是结构共享。**建议：types/ 只在多模块真有共享时建（如 AccountInfo / FarmSnapshot），不照搬 7 个文件。**
4. **activity-data/constellation-2026072701.json** — 是 v2026-07-27 的活动数据，要不要拉最新？
5. **wx-login 微信扫码登录** — 需要小程序 appid/secret，这块要不要接真实 API？

## 6. 建议的下一步

**先做 1F 基础设施层**（types + utils + config + models + json-db + rate-limiter，~6 个 commit、~3500 行）。理由：
- 这些是所有上层 service 的依赖
- 没有这层，service 都在用裸字符串/JSON，跟原项目对不齐
- 体量适中，能在几次会话内完成
- 写完后再做 service 层，能在每个 service 上引用类型，对照原 TS 不会乱

**然后 1G service 层**（~14,000 行、~14 个 commit），按依赖顺序一波推完。
**最后 1H runtime + core/worker 编排 + 2A controllers**（~6,000 行、~10 个 commit）。
**2B 联调 + 内存对比** 收尾。
